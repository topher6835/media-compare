## What Currently Works

- SQL Flyway V9 adds successful-only `preview_asset` metadata without altering existing catalog rows. Immutable key/domain/layout validation, current FileEntry evidence lookup, and read-only `/api/previews/{assetKey}` serving are implemented. Assets use `media-compare.preview-cache-root` (default `data/cache/previews`); no actual generator exists yet.
- SQL Flyway V8 adds `media_relationship` as the fifteenth application table without changing existing catalog rows. Typed Java domain/repository behavior and pure enabled-edge connected components are tested. No REST or frontend changes expose this foundation yet.
- V1–V5 migrations retain their historical meaning. Transactional Java Flyway V6 rebuilds FileEntry, backfills one SourceMembership per V5 row, verifies preserved IDs/content/metadata/provenance and foreign keys, and enforces resolved identity uniqueness, active membership path uniqueness, and the paired Source/context authority-revision CHECK. Partial V5 scan provenance remains legal.
- Transactional Java Flyway V7 creates `source_binding_period` and backfills one exact open period for each currently bound Source. Unbound Sources get none. It rejects partial Source binding shapes, checks foreign keys, and leaves existing catalog rows unchanged. Period constraints enforce unique bound revisions, one open period per Source, and paired chronological closing fields.
- LocationContext creation, acceptance, retirement, same-anchor replacement, and explicit first-time local macOS/APFS Source binding remain implemented. Valid legacy raw acceptance is persisted history but not current authority; malformed current acceptance remains an integrity failure.
- Standalone macOS/APFS logical-anchor discovery keeps the Source path in the visible namespace. The trusted APFS mount inspector supplies Volume UUID observations for the root and visible ancestors; the resolver rechecks every observation and exact spelling and fails closed on unavailable or unstable evidence. Structural containment and binding guards are unchanged.
- Explicit Source preparation uses that anchor to reuse an applicable ACTIVE context or create one through guarded activation, accepts review-required context evidence when valid, and calls the existing first-binding service after fresh probes. READY, PREPARATION_REQUIRED, and REBIND_REQUIRED are derived from durable Source shape; prepare is idempotent for READY and refuses structured-unbound Sources. Probes run outside database write transactions.
- First binding now inserts its matching open period atomically with the guarded Source update under the existing SQLite writer reservation. A period-insert failure rolls back the Source update. Current binding and v3 admission/publication authority still come only from the Source row and `SourceBindingAuthority`.
- Explicit unbinding reserves the SQLite writer, verifies the current bound Source against its exact open period, then atomically closes that period, retires all ACTIVE memberships, and clears current Source context/evidence. It advances Source revision once while preserving the structured root path, dialect, and canonical key. It performs no filesystem probe and no missing claim. Retired memberships retain presence and provenance; FileEntry, content, hash, and analysis artifacts survive. Missing or contradictory history and failed writes roll back the transition.
- Explicit rebinding requires a structured-unbound Source, matching latest closed period, no open period, and zero ACTIVE memberships. It accepts fresh context/root evidence for the same or a different current accepted LocationContext through the APFS validation shared with first binding. A writer-reserved transaction preserves Source ID/root path/key/dialect, advances revision once, writes new current evidence/context, and creates one matching open period. Closed history and retired memberships remain unchanged. Only a later trusted positive observation can reactivate a membership for the same resolved FileEntry; another context does not imply FileEntry/content equivalence.
- Explicit relocate-and-bind requires a caller-selected different new Unix root and target LocationContext, a structured-unbound Source whose old root matches its latest closed period, no open period, and zero ACTIVE memberships. Fresh accepted context/root evidence must describe the new root and resulting Source/context revisions. One writer-reserved transaction changes the Source root path/key and current binding, advances revision once, and opens a new period snapshotting the new root. Old periods, retired memberships, FileEntries, content, and analyses stay unchanged. Stale old-root/context scan work fails closed; only later trusted observations establish current memberships. No automatic remount recognition or historical identity inference is implemented.
- The nested/overlapping Source milestone is complete for the supported local macOS/APFS profile. Source-independent FileEntries can have separate SourceMemberships for each overlapping Source; end-to-end v3 acceptance confirms scan-order independence, repeat-scan stability, Source-local reconciliation, and physical duplicate/storage counting by FileEntry.
- V3 admission requires every requested Source to have current supported bound local macOS/APFS authority. It is all-or-nothing and does no filesystem probe. Unbound, unsupported, Windows-host, and legacy-raw acceptance Sources cannot start new v3 work.
- V3 retains `DISCOVERY -> RECONCILIATION -> CONTENT_ASSIGNMENT -> CONTENT_HASHING -> COMPLETED`. Fresh context/root probes and a mount-aware directory walk run outside write transactions. Structured `df` mount-point evidence plus `diskutil` APFS identity reject child mounts even if the UUID matches; uncertain storage and symbolic links fail closed. The pure scan authority contract qualifies exact resolved candidates and complete-traversal missing claims.
- Writer-reserved short transactions reread Source/context authority, resolve FileEntry by `(location_context_id, location_key)`, validate canonical structured location and containment, and publish a SourceMembership. Legacy unresolved active-path collisions are retired atomically without retargeting history. Byte evidence change advances FileEntry revision and clears content; membership presence alone does not. Trusted reconciliation changes only the scanned Source's ACTIVE memberships and never makes a missing claim after incomplete traversal.
- Assignment, exact hashing, and media-metadata live candidate selection require a current ACTIVE/PRESENT trusted membership and RESOLVED FileEntry. Publication rechecks the persisted authority, path relationship, and candidate revisions. Hashing and media metadata use resolved absolute paths with file-evidence checks. Historical content/analysis remains readable.
- Exact duplicate grouping counts distinct FileEntries for physical copies and savings; Source counts and relative path details use memberships. The frontend groups Source paths by physical FileEntry and offers keeper/removal previews and explicit multi-group browser-session cleanup planning for complete groups, independent of filter matches. Plan entries and totals use physical FileEntries, never membership counts.
- Historical v1/v2 Jobs and ScanRuns remain readable. Their old discovery/reconciliation writers are closed after V6; startup recovery fails incompatible active v1/v2 work and interrupted v3 work. The public indexing start/polling path routes new work to v3.

## Known Limitations / Not Yet Implemented

- Relationship rows have no producing matcher or automatic exact-hash adapter/projection yet. The repository returns all retained versions/configurations; compatibility selection, actual non-exact detection, and album query API/UI remain unimplemented. Groups are deliberately not persisted.
- Preview identity/persistence/layout/HTTP serving are implemented, but there is no actual thumbnail/image/video generation/publication orchestration, pixel-size/format policy, background preview queue, or cache eviction/cleanup. Tests use temporary cache files, not generated previews. Real Windows filesystem/junction acceptance remains manual.
- Only the tested local macOS/APFS binding profile can execute v3 scans. Windows, network, and other provider profiles remain future work. Automatic remount recognition, automatic membership reactivation during binding transitions, multiple active catalogs, catalog switching, automatic historical merge, and the shortened SCAN are not implemented.
- Preparation is first-time only. Previously bound structured-unbound Sources show REBIND_REQUIRED; no rebinding action is available in the UI.
- Valid migrated unresolved history remains separate and is never inferred to equal a newly resolved FileEntry. A later trusted observation may retire the old path membership while preserving its ContentRecord and analyses.
- The future shortened scan ending after assignment is execution version 4 or later; v3 still includes exact hashing.
- Cleanup plans are session snapshots only. Full reload clears them. Frontend read-only preflight is implemented with transient, immediately stale results; it does not authorize file operations. No durable review decisions or Trash/delete/move operation exists; future execution must revalidate immediately before mutation. Only the existing local macOS/APFS authority profile can pass preflight; other profiles fail closed.
