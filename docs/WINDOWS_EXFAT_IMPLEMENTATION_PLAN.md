## 1. Constraints and production seams

Every independent positive after a protected file handle closes creates a new occurrence, even with equal path, timestamps, legacy index and SHA-256. Every exFAT positive requires full fresh SHA-256 from its own protected handle. Exact means equal bytes and length; it never merges physical occurrences or ContentRecords. Ordinary root-window closure leaves durable configuration, revisions, open binding periods and last-known memberships unchanged. A closed window requires explicit Prepare/Accept; loss of authority is not absence. Persisted physical reveal and cleanup preflight remain unavailable. ExFAT Session storage is excluded. NTFS/APFS behavior stays intact.

All Java paths below are relative to `backend/src/main/java/io/github/topher6835/mediacompare/`, unless explicitly stated otherwise. The seam table and **new** labels record the original scoping baseline/proposals; the Slice 1-4 progress annotations above identify the now-implemented disabled foundations. Slice 5-6 proposals remain unimplemented.

## 2. Filesystem dispatch and native abstraction

### Dispatch

Extend the existing host boundary. `HostFileSystems.select` returns **new** `WindowsHostFileSystem` on Windows; it delegates NTFS checks to the existing adapter and routes protected exFAT operations to **new** `WindowsExfatHostFileSystem`. Add a small filesystem-profile value and a per-path detection operation to `HostFileSystem`; keep catalog path rendering independent of detection. The macOS implementation retains its APFS probe/authority behavior. Unsupported host, unsupported filesystem and IO uncertainty stay distinct denied outcomes.

**New** `WindowsVolumeProbe` obtains native filesystem type/drive type/route information and NIO FileStore type outside write transactions. First preparation detects freshly before selecting a writer. Reacquisition, admission preflight, each directory/file acquisition, original read and scan completion detect/recheck again. Stored evidence chooses the expected profile, never establishes today's filesystem. Require exFAT native/NIO agreement, local fixed/removable ordinary drive paths, serial/GUID agreement and no redirected route. NTFS errors do not cause exFAT fallback. Preserve existing NTFS native IDs and profile-specific checks; do not reinterpret its serial as exFAT's eight-digit serial.

Replace OS inference using `instanceof WindowsNtfsHostFileSystem` in `SourcePreparationService`, `CurrentLocationAuthority`, `Version3AuthorityCapture`, `Version3ScanExecutionService`, and `WindowsNtfsPathInspector` with explicit host/profile queries. Keep `WindowsNtfsPathInspector` callable only for NTFS; its own guards must work under the new facade. `ScanAuthoritySnapshot` needs an explicit profile and an optional exFAT snapshot (window reference and observations); `windowsNtfs()` may remain for existing branches, but "not NTFS" must no longer imply APFS. Add **new** `WindowsExfatScanAuthority` rather than overloading `WindowsNtfsScanAuthority`.

Reject UNC/network/mapped drives, device paths, SUBST/redirection, directory mounts and simultaneous ambiguous volume aliases for exFAT. Compare native extended final paths only after strict decoding; do not admit that syntax as user configuration. Resolve enumerated exact spelling before storing lp1/lk1; ambiguous Windows case/spelling fails closed. This is limited host resolution, not global catalog folding.

### Native choice

Choose a **separate `WindowsExfatNative`**, behind a narrow injectable **new** `WindowsExfatNativeAccess` interface used by the exFAT host adapter/registry. The common caller-facing interface remains `HostFileSystem`; NTFS and exFAT do not need a generic native identity interface. NTFS's current short observation API and sharing assumptions differ materially from retained exFAT leases, so expanding `WindowsNtfsNative.Observation` would blur authority semantics and increase regression risk.

Expose Java-only `AutoCloseable` directory/file lease types, observations and a seekable read channel; no JNA HANDLE/Pointer escapes. Directory opens use GENERIC_READ, OPEN_EXISTING, BACKUP_SEMANTICS + OPEN_REPARSE_POINT and SHARE_READ|SHARE_WRITE, without DELETE. Files use GENERIC_READ, OPEN_EXISTING, OPEN_REPARSE_POINT and SHARE_READ only. Confirm non-inheritance. Share-mode checks persist until closure. These sharing/no-follow parameters follow [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), with empirical effects limited to the recorded qualification.

Reuse the qualified portions of `backend/diagnostics/RetainedHandleNative.java`: CreateFile, GetHandleInformation, legacy GetFileInformationByHandle layout, GetFinalPathNameByHandle, GetVolumeInformation, GetVolumeNameForVolumeMountPoint, SetFilePointerEx, ReadFile, immediate native-error capture and deterministic CloseHandle. Production adds streaming SHA with a fixed buffer (not whole-file buffering), checked byte totals/offsets, strict buffer lengths/unsigned conversions, cancellation checkpoints, bounded final-path buffers, idempotent ownership and partial-acquisition cleanup. Never close a handle concurrently with a channel read and then recycle its numeric value.

Every lease reconciles native attributes, serial, size/exact mtime and final route with NIO no-follow classification and today's volume. Reject reparse bit, link/isOther, follow/no-follow disagreement, wrong type, storage boundary, IO/invalid handle or lineage uncertainty. Legacy index is operation-local contradiction evidence only, never a reusable physical ID. Directory mtimes can change normally as children are enumerated; do not require all directory timestamps to remain frozen. File byte-version observations must remain coherent; do not invent two-second normalization.

Do not copy fixture writes/deletes/moves/time setters, writable mapping experiments, Z:/serial/VeraCrypt-device constants, owner markers, command-file polling, checkpoint/PID replay, test deadlines, raw-content Base64 logging, global diagnostic open counters or the 4096-byte fixture `readAll` limit into production. QueryDosDevice may detect unsupported route aliases, but a VeraCrypt-specific name is not a production identity requirement. No new dependency or shell subprocess is needed.

## 3. Process-local authority windows

Slice 3 implements the internal registry/lifecycle described here with production disabled. Each Source owns its own retained drive-to-root chain; actual directory reservations/handles are counted conservatively without a shared directory pool. Slice 4 implements SCAN bundle admission/progress/shared traversal and separates IO resource retention from short publication leases. Metadata/preview coordination remains Slices 5-6. The exact runtime/context/revision/route/continuous-lifetime restriction below remains mandatory for any later directory pooling.

**New** `filesystem/ExfatAuthorityWindowRegistry` is a Spring component owned by the selected catalog runtime, depending on `CatalogPaths`/`CatalogOwnership`. It starts empty. A runtime UUID distinguishes different Session lifetimes; do not put it in `session.json`. Keys are `(runtimeUuid, sourceId, windowUuid)` plus indexes by Source and owning bundle/Job. A window captures exact Source/context rows, open-period snapshot, configured/resolved root, context/Source revisions, native volume signals, retained root chain, phase, cancellation flag and outstanding operation leases.

Use internal phases PREPARED, IN_BUNDLE, HANDOFF, REVOKED and CLOSED. These are process-local implementation states, not new database or durable Job statuses. Prepared authority is available for one bundle, not a permanent service. Admission consumes/associates the exact prepared UUID with a fresh bundle UUID and accepted SCAN Job. Record bundle -> ScanRun/SCAN Job -> metadata Job/preview tasks in memory. Capture references in all closures/candidates/claims/receipts. No worker calls "find current window for Source" to authorize previously admitted work. A later UUID at identical revisions is unrelated; old requests/receipts cannot be renewed.

### Synchronization and transaction ordering

Use one small registry monitor for maps, phases and handle reference counts, and one runtime publication gate (read/write lock). Do not hold the monitor during native IO, hashing, decoder work, SQLite waiting or queue draining. A publication holds the gate's read side across a separately proxied short writer transaction **through commit**; recheck exact UUID, bundle/Job, cancellation and captured/current catalog shape while holding it. Invalidation/install/durable exFAT transitions take the gate's write side. All such code acquires this gate before entering the SQLite writer transaction; never acquire it from inside a writer-reserved transaction after another thread has acquired the gate and is waiting for that writer.

Current `@Transactional` writers need small nontransactional exFAT coordinators around their transactional methods (or a TransactionTemplate scoped to that same outer gate). An in-method lock released before Spring's proxy commits is insufficient. Unbind/context retirement/replacement must follow this same ordering; split only these entry points as necessary rather than refactoring unrelated persistence. Successful durable transitions revoke affected windows before releasing the gate. Conservative revocation on a rejected transition may close a runtime window but must not partially change durable rows.

Native acquisition/large reads happen outside this gate. At acquisition start register an attempt UUID and capture an installation/invalidation generation; at final installation under the gate reject changed generations, shutdown or cancellation of that exact attempt, as well as changed catalog state. Release of an existing window also cancels its in-flight revalidation; release of a missing/closed old UUID must not increment the generation or cancel an unrelated newer Prepare attempt. Shutdown/expiry closes pending acquisition attempts as well as installed windows. Install only after a committed initial bind, or a short writer-reserved no-change reread for reacquisition. Failure closes every newly acquired handle. Scheduling happens after DB commit; rejection fails the accepted Job and revokes its bundle.

### Lifecycle and shared handles

Hold drive-root and every ancestor through each explicitly accepted Source root. Share reference-counted directory leases only within the same runtime, accepted context revision, verified volume route and continuously held handle lifetime. Sources retain separate acceptance snapshots/window UUIDs and bundle membership. Accepting A never grants B authority. Releasing idle A drops only A's references; B's drive handle can still prevent dismount. Releasing one member of a running multi-Source bundle cancels the whole bundle, while unrelated prepared windows remain independently releasable. A drive/context route failure revokes every window using that uncertain shared chain.

During traversal hold descendant directories in a depth-first stack and only one observation file at a time for the indexing worker. Content readers own their own file leases. Bound shared directory handles, depth, prepared Source count and queues; no handle per historical FileEntry and no digest map surviving stages. Approved starting parameters for this implementation scope: 5-minute unused-Prepare timeout, 2-minute metadata handoff timeout, 30-second release/shutdown drain budget, 64 prepared Source windows, 4096 retained directory handles and depth 256. Exceeding a bound denies acquisition/marks traversal incomplete; it never silently releases an ancestor or reacquires it. These resource limits may reject an otherwise valid 1000-Source API selection; they do not change its syntactic maximum. Running operations check cancellation between buffer reads and directory entries; a configurable no-progress deadline revokes stalled work, not a hard elapsed-time limit on large healthy scans.

Revoke on explicit Release, bundle success/failure/cancellation, true unbind/context transition, required-handle loss, volume/route uncertainty, expiry or Session shutdown. Revocation blocks publication and admission, cancels pending exact-window tasks and requests worker interruption; leases close in finally and shared directories close after their last user drains. On shutdown revoke before executor draining, preserve existing CatalogOwnership retention if a worker outlives shutdown, and close registry resources before releasing catalog ownership.

Do not claim that Java interruption guarantees a deadline for a stuck synchronous Win32 call. Release has a bounded response and reports draining until operations actually close; closure failure remains visible and never restores authority. Do not forcibly close an in-use handle, force VeraCrypt dismount or report all handles released prematurely. A stuck provider can require process exit to release its handles. This is a residual operational limit, not authorization for a later window.

Release first marks the exact window as closing under the registry monitor, blocking new admission and setting cancellation without waiting for SQLite. Acquire the publication gate's write side within the remaining drain budget. A transaction already holding its read side may finish before revocation linearizes; do not close its retained handles concurrently. If that transaction outlives the budget, return DRAINING/live=false and finish revocation/closure asynchronously once it leaves the gate. Never report RELEASED until both publication and handle users have drained. Test this ordering with a deliberately paused commit.

## 4. Prepare/Accept, release and bundle API

Keep `POST /api/sources/{id}/prepare` without a body, existing durable fields and PREPARATION_REQUIRED/READY/REBIND_REQUIRED meanings. Extend `SourceResponse` with `filesystemProfile` (APFS/NTFS/EXFAT/null, from stored evidence), `liveAuthorityAvailable` (`Boolean`: null for profiles not requiring a window, false/true for exFAT), and `liveAuthorityWindowId` (UUID or null). ExFAT true means a currently valid retained window exists; it is a transient projection, not a physical guarantee or reservation. GET performs catalog/registry projection only; it must not probe/acquire authority. No-store responses are required. Project stale snapshots as unavailable, never repair them.

| Prepare case | Proposed behavior |
| --- | --- |
| Never bound, exFAT | Fresh detect, direct spelling/separation checks and protected chain; create/reuse logical context, accept REVIEW_REQUIRED context with no bound Sources, bind and open period under existing invariants; install initial window only after commit. |
| Bound exFAT, no window | Strictly validate existing Source/context envelopes and matching open period; explicitly accept today's root, acquire fresh chain, verify required type/serial/GUID/configuration and reread unchanged rows; install new UUID. No durable rewrite/revision/period/membership change. |
| Bound exFAT, live window | Freshly revalidate retained root/volume/route/separation; return same UUID if valid. Do not extend an active bundle's lifetime or replace its window. An invalid window is revoked and the request fails; user must explicitly Prepare again. |
| Structured-unbound exFAT | Keep REBIND_REQUIRED and 409 STATE_CHANGED; use a separately explicit true rebind, never first-prepare or automatic resurrection. |
| NTFS/APFS | Preserve READY early return and first-time preparation. New transient fields do not add a window requirement. |
| App restart/same-letter ordinary remount | Bound Source remains READY; live=false, window=null. Explicit Prepare/Accept reacquires without unbind/rebind. |

Existing 422 PATH_UNAVAILABLE/PROFILE_UNSUPPORTED/EVIDENCE_UNCERTAIN, 503 PROBE_ERROR and 409 STATE_CHANGED remain applicable. Required-volume mismatch denies automatic use and explains the durable replacement route; supplemental root-index/time changes after a gap are not such a mismatch. Resource-limit denial can use bounded EVIDENCE_UNCERTAIN initially; do not return a misleading READY/live=true. Preserve coherent infrastructure failures separately.

Add `POST /api/sources/{id}/release-authority` with `{ "windowId": "UUID" }`. Target the exact window so a delayed release cannot close a newer one. Return 200 with the updated Source projection and `releaseState: RELEASED | DRAINING`, and `otherWindowsOnVolumeRemain: boolean`. A missing/already closed exact UUID is idempotent; it never revokes a different current UUID. Unknown Source is 404. Malformed UUID is 400. Release itself changes no durable binding/membership. A release of running work is explicit cancellation: use existing FAILED Job/recovery shape, not a new durable CANCELLED status. UI says all affected Sources may need releasing before VeraCrypt dismount; RELEASED for one Source does not claim the volume is globally idle.

Extend indexing request with optional `authorityWindows: [{sourceId, windowId}]`, required exactly for selected exFAT Sources. Validate distinct canonical IDs. Native Sources need no entries. Capture an immutable expected-window set before queued submission; existing HTTP replays return the original execution and never attach replacement windows or resubmit. Maintain request-key identity by Source set; the replayed windows are not credentials. Direct `Version3ScanExecutionService.create`/background entry points must also require the exact set; protecting only the public controller is insufficient.

Preserve the four durable SCAN stages. Successful exFAT SCAN enters a bounded in-memory metadata HANDOFF rather than closing roots at SCAN completion. Extend `POST /api/media-metadata-runs` with an optional body `{indexingScanRunId}`. The exFAT UI passes that ID; backend binds the new metadata Job to that scan's existing bundle/windows before submission. Retry of this handoff returns the associated Job while that bundle remains live. Another unrelated active metadata Job is a conflict, not the bundle's follow-up. Keep `job.scan_run_id = NULL` and metadata execution version 1; association lives only in the registry. The existing global/no-body metadata operation may process native-profile candidates, but cannot borrow exFAT windows acquired after its admission. It must capture any explicitly supplied exFAT window set when accepted, or treat those originals as unavailable. Apply registry restrictions to the selected exFAT subset while preserving native candidates' behavior.

The metadata UI must follow the returned associated Job ID for exFAT, not infer association from creation time/latest status. On handoff expiry, metadata admission fails; completed indexing stays completed. Fresh explicit Prepare may authorize a **new standalone content-read/metadata bundle**, but cannot resume assignment/hash work from the old scan. Extend standalone metadata body with optional `authorityWindows` for this retry use, mutually exclusive with `indexingScanRunId`. Existing failure/recovery and completed analysis artifacts remain readable.

Preview tasks admitted during a bundle capture its exact window references and may drain before its terminal closure. Minimum V1 does not add automatic whole-Source thumbnail generation. Existing visible-thumbnail scheduling after the completed indexing/metadata bundle therefore needs a fresh explicit Prepare for an exFAT content-read bundle; it cannot reopen roots automatically. Extend `ThumbnailScheduleRequest` with optional `authorityWindows` and per-file response with AUTHORITY_UNAVAILABLE. A prepared window can be consumed by one finite submitted thumbnail batch (existing maximum 100 IDs, queue 64); close after that batch drains, including unsupported/failing tasks. Capture FileEntry/content/membership revisions and the selected qualifying Source/window at scheduling; executor-time revalidation cannot substitute a newer window. Additional batches require new explicit acceptance after closure. Surface this limited workflow clearly; background-preview UX expansion is later work.

## 5. Exact occurrence and receipt migration design

Slice 2 implements Flyway **V10** at `backend/src/main/resources/db/migration/V10__add_exfat_occurrence_evidence.sql`. The approved SQL below is unchanged. Runtime/profile authority and publication described in later sections remain unimplemented.

Add two columns to `file_entry`, leaving old rows null:

| Column | Shape | Meaning |
| --- | --- | --- |
| `occurrence_token` | nullable TEXT COLLATE BINARY; canonical lowercase UUID | Application-issued identity of one captured exFAT occurrence; globally unique when present. |
| `observation_evidence_json` | nullable TEXT; UTF-8 encoded length 1..1048576 bytes when present | Immutable versioned receipt for that occurrence. Both fields null or both non-null; non-null requires RESOLVED. |

Use two ADD COLUMN statements, token first and receipt second. Put the cross-column pair/RESOLVED/length CHECK on the second column; avoid a FileEntry rebuild. V6's "no incoming FK" rationale no longer applies: SourceMembership and PreviewAsset reference FileEntry now. Keep foreign_keys enabled and preserve every existing field/ID/FK. ADD COLUMN may carry CHECK constraints and validates existing rows, as described by [SQLite ALTER TABLE](https://www.sqlite.org/lang_altertable.html). Implementation must test these exact statements with the pinned SQLite 3.50.3.0, not assume features from a newer SQLite website release.

For the token column, CHECK null or TEXT, length=36, hyphens at positions 9/14/19/24, 32 hex characters after removing hyphens, and no character outside lowercase 0-9/a-f after removal. The implemented codec verifies canonical lowercase UUID text and IETF variant-2/version-4 semantics for occurrence/context/bundle/window IDs; OS volume GUID routes have separate canonical validation. For the receipt column, CHECK `(token IS NULL AND receipt IS NULL) OR (token IS NOT NULL AND receipt IS NOT NULL AND typeof(receipt)='text' AND length(CAST(receipt AS BLOB)) BETWEEN 1 AND 1048576 AND location_identity_status='RESOLVED')`. Use explicit IS NULL predicates to avoid SQLite CHECK's nullable-result acceptance. JSON parsing/version/profile/path/revision/length/digest validation belongs in the strict Java codec; SQL does not establish a valid receipt just because it is text. No JSON-expression index is needed.

Replace and add these indexes, in the same migration transaction:

| Index | Exact columns/predicate |
| --- | --- |
| `uq_file_entry_resolved_location` (drop/recreate) | UNIQUE `(location_context_id, location_key)` WHERE `location_identity_status='RESOLVED' AND occurrence_token IS NULL` |
| `uq_file_entry_occurrence_token` (new) | UNIQUE `(occurrence_token)` WHERE `occurrence_token IS NOT NULL` |
| `idx_file_entry_exfat_location` (new) | Nonunique `(location_context_id, location_key, id)` WHERE `location_identity_status='RESOLVED' AND occurrence_token IS NOT NULL` |

The global token index is stronger than `(context,key,token)` and makes receipt lookup deterministic. Native null-token rows retain their exact address uniqueness. The nonunique index supports historical lookup and path supersession. Preserve all membership, content/extension, binding-history, Job and preview indexes. No current/active flag belongs on FileEntry: applicability/presence still live on memberships.

        AND substr(occurrence_token, 24, 1) = '-'

        AND replace(occurrence_token, '-', '') NOT GLOB '*[^0-9a-f]*'
    ));
ALTER TABLE file_entry ADD COLUMN observation_evidence_json TEXT
    CHECK ((occurrence_token IS NULL AND observation_evidence_json IS NULL)
        OR (occurrence_token IS NOT NULL AND observation_evidence_json IS NOT NULL
            AND typeof(observation_evidence_json) = 'text'
            AND length(CAST(observation_evidence_json AS BLOB)) BETWEEN 1 AND 1048576

DROP INDEX uq_file_entry_resolved_location;
CREATE UNIQUE INDEX uq_file_entry_resolved_location
    ON file_entry(location_context_id, location_key)
    WHERE location_identity_status = 'RESOLVED' AND occurrence_token IS NULL;
CREATE UNIQUE INDEX uq_file_entry_occurrence_token ON file_entry(occurrence_token)
    WHERE occurrence_token IS NOT NULL;
CREATE INDEX idx_file_entry_exfat_location
    ON file_entry(location_context_id, location_key, id)

### Receipt on FileEntry

Store it on FileEntry, because one retained physical observation may authorize several memberships and later stages. A ScanRunSource row is an aggregate for a whole traversal and a membership would duplicate the receipt. Do not add another receipt table.

Strict **new** `ExfatObservationReceipt`/codec version `windows-exfat-observation-v1` contains: occurrence token; FileEntry observation revision (initially zero); absolute lp1/lk1 and context ID/revision; captured size/byte count/full lowercase SHA-256; exact mtime; bounded before/after classification/final-route/serial/GUID evidence; observation start/finish; bundle UUID, ScanRun ID and SCAN Job ID; each qualifying Source ID/revision/root/path key, exact window UUID, resulting membership ID/revision, ScanRunSource ID/generation and relative route. No HANDLE or raw file bytes. Legacy index, if included, is explicitly contradiction-only evidence. Source arrays are deterministically ordered, unique, capped at the indexing selection maximum and bounded by the receipt byte cap; overflow rejects the whole positive, not a truncated receipt.

Preallocate the one FileEntry ID and participating membership IDs **under the already reserved SQLite writer**, using each table's maximum integer primary key plus checked increments (empty table starts at 1). These tables use ordinary INTEGER PRIMARY KEY, not AUTOINCREMENT. Reject exhausted integer range. Add dedicated exFAT insertion methods accepting these IDs; keep native generated-key insertion unchanged. This lets the writer encode the final receipt with resulting membership IDs/revision zero before inserting the FileEntry, then insert its memberships and commit all rows while the file is held. No provisional receipt or staging row is needed. Concurrent writers cannot allocate the same IDs under the reservation. Rollback may reuse never-committed numeric IDs, but never a committed occurrence token. Test this construction with existing rows and concurrent admissions.

After commit the receipt is immutable provenance; assignment/hash consumption is represented by the attached ContentRecord and completed AnalysisRecord, not a mutable "used" flag. Old receipt UUIDs never reconstruct authority. Missing/invalid/mismatched receipt fails processing; never repair by reopening. Historical receipt and completed artifacts survive supersession, failed scans, release and restart. No cleanup/retention policy is added.

## 6. Discovery, overlap and guarded publication

Keep native-profile walks and batching unchanged. Add **new** `WindowsExfatDiscoveryWalker` used by an exFAT branch in `Version3DiscoveryService`. Group selected exFAT Sources by verified current context and maximal selected roots: traverse a containing root once and fan each path out to the selected prepared roots that structurally contain it. Disjoint roots still walk separately. Start every participating ScanRunSource/generation before shared publication; preserve per-Source completion/coverage. No unselected or unprepared Source receives a new positive.

For each file:

1. With accepted root leases held, acquire/validate all directories through the parent. Enumerate exact spelling and reject uncertain aliases/storage/classification. Hold this full chain until publication ends.
2. Open exactly one protected regular-file handle for the physical positive; capture native/NIO/volume/route evidence. Capture each participating Source's exact window and catalog route, not just the parent Source's authority.
3. Read all bytes through that handle with streaming SHA-256/count outside any SQLite write transaction. No metadata/cache shortcut. Check cancellation, length, file/route evidence again while held.
4. Issue a fresh occurrence UUID. Enter the registry publication gate and one short transaction (**new** `ExfatObservationPublicationService` coordinating the profile-specific method on `SourceMembershipPublicationService`). Reserve the writer and verify bundle/Job/stage are RUNNING/DISCOVERY, exact window set, unchanged Source/context/open periods, all ScanRunSource DISCOVERING/generations and path coherence.
5. Find **all** older token FileEntries at that exact verified context/address and retire their ACTIVE memberships across Sources, incrementing membership revision with checked overflow. Include ACTIVE MISSING routes; presence values are left unchanged. Also retire legitimate migrated UNRESOLVED path collisions for participating Sources under the existing history rule. A native-profile resolved collision is an integrity/profile contradiction, not something to retire opportunistically.
6. Insert one fresh resolved token FileEntry at observation revision zero and one ACTIVE/PRESENT membership for every qualifying selected Source. Bind the final receipt to these exact IDs/revisions/routes and commit it with the positive. Update discovery progress in that transaction. Assert no other token at that verified path retains an ACTIVE route. Unselected overlapping Sources' old routes retire; they receive no replacement membership until observed themselves.
7. After commit, leave the publication gate and close the file lease in finally. DB rejection rolls back supersession, insertion, receipt and progress, then closes the file. Close failure invalidates the window and fails the bundle; already committed historical evidence survives.

Hashing is outside the transaction; authority is checked again before the short commit. No delayed exFAT batch holds closed file candidates. Different physical positives never reuse a token; only fanout from the same retained observation does. Progress should consistently count published physical observations, while per-Source traversal coverage records each membership; document this exFAT difference without changing result schema.

Supersession must also include historical spelling variants after a case-only rename. Exact lk1 equality alone is insufficient. Page the context's ACTIVE exFAT catalog routes and compare their decoded Windows paths against the newly enumerated, protected route using host path comparison; use case-insensitive comparison only to identify alias candidates. Verify those candidates against the held chain's exact enumerated spelling, retire equivalent old routes in the same writer, and reject unresolved/ambiguous aliases. Do not follow historical paths outside that protected chain, persist folded keys, or infer physical identity from spelling. Include unselected overlapping Sources and ancestor spelling changes in these tests.

Start/end captures and each missing claim carry the exact window/bundle/generation. After all relevant directory visits succeed and fresh end checks pass, existing completion/reconciliation writers may sweep only that Source's ACTIVE unseen memberships. Invalid handle, share conflict, inaccessible subtree, alias/storage uncertainty, resource limit or cancellation makes traversal incomplete. No missing sweep follows incomplete discovery, even if earlier qualified positives committed. An old claim cannot survive release/reacquisition at identical durable revisions. Directory enumeration remains non-atomic; frozen ordinary-operation race limits remain explicit.
