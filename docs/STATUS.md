# Status

## Current State

Media Compare is a fresh v2 repository with a working full-stack scaffold. The backend retains public version-1 indexing endpoints and provides a public background version-2 lifecycle in which one durable SCAN Job owns DISCOVERY, RECONCILIATION, CONTENT_ASSIGNMENT, and CONTENT_HASHING. It also derives and catalog-correctly filters exact duplicate groups through REST. Typed media-metadata persistence, stale-evidence publication safety, real ImageIO extraction, a durable image-metadata Job with narrow manual REST start/read endpoints, the pure ffprobe interpreter plus bounded process runner, a pure cross-platform structured-location codec, and a dormant macOS exact-spelling/local-APFS continuity probe are implemented; durable video-metadata integration, automatic scheduling, and frontend metadata display remain deferred. The frontend can register and browse Sources, launch and reconstruct durable version-2 indexing, follow persisted stage/results state, then browse/filter exact duplicate groups and inspect complete group/member/occurrence context. Broader library/review workflows, similarity matching, materialized decisions, and cleanup are not implemented.

The backend is a Java 21 and Spring Boot 4.1.1 Maven application. It connects to a local SQLite database, starts Flyway, exposes `GET /api/health`, provides Source endpoints under `/api/sources`, scan-request endpoints under `/api/scan-runs`, execution-handoff endpoints under `/api/scan-runs/{id}/execution`, synchronous DISCOVERY and RECONCILIATION POST endpoints, `POST /api/scan-runs/{id}/content-assignment`, `POST /api/scan-runs/{id}/content-hashing`, and read-only exact duplicate endpoints under `/api/exact-duplicate-groups`. The frontend is a React and TypeScript Vite application with React Router. Its `/` route retains the health check and directs users to Sources or Exact Duplicates; `/sources` registers/lists Sources and orchestrates indexing; `/duplicates` browses and filters aggregate summaries; and `/duplicates/:digestHex` shows complete group, member, occurrence, and filter-match context.

The reviewed persistence foundation is implemented. Flyway migration `V1__create_core_schema.sql` creates the initial eleven application tables with their structural constraints, foreign keys, and indexes. Java Flyway migration `V2__add_file_entry_extension_key` adds nullable normalized FileEntry extension metadata, bounded backfill, and its lookup index. SQL migration `V3__add_durable_indexing_foundation.sql` adds durable indexing primitives, and V4 adds nullable `analysis_record.result_json`. V5 adds the `location_context` table and nullable, still-dormant Source binding fields, bringing the application schema to twelve tables. Immutable Java records and focused Spring JDBC repositories map the fields. Exclusive local catalog ownership, bounded background execution, startup interruption recovery, public v2 atomic start/read contracts, and the React polling cutover are implemented.

V5 provides durable LocationContext rows and nullable Source binding fields. Transactional services create caller-supplied ACTIVE REVIEW_REQUIRED contexts with structural-overlap enforcement, explicitly accept an observed local APFS context, retire unbound ACTIVE contexts with revision and timestamp guards, and atomically replace an unbound ACTIVE context at the same structured anchor with a new review-required context. The pure location layer implements host-independent `unix`, `win-drive`, and restricted `win-unc` parsing, structured `lp1` paths, deterministic `lk1` keys, and structural containment. Typed version-1 macOS local-APFS context and Source-root evidence, strict bounded JSON codecs, pure continuity comparison, exact-spelling resolution, and bounded evidence capture are also implemented. Existing Sources remain unbound, Source registration creates no context, and current indexing neither requires nor consults LocationContext. The wider approved target remains planned: separate SQLite files for independent catalogs; overlapping Sources connected to source-independent FileEntries through current SourceMemberships; membership-owned presence; passive restore/rebinding; and a future SCAN semantic that ends after reconciliation/assignment, with hashing as a separate explicit operation. Source binding and operational context use remain future work.

## What Currently Works

- The pure `location` package parses ordinary absolute Unix paths, restricted drive-rooted Windows paths, and restricted UNC paths without using the host filesystem. It preserves accepted case and Unicode spelling, rejects unsafe or ambiguous syntax, compares hierarchy by dialect/root/component structure, writes strict bounded `lp1` JSON, and writes strict bounded deterministic `lk1` binary keys as lowercase hex. A pure fail-closed `LocationAnchorPolicy` validates persisted anchor path/key pairs through the existing codecs—rejecting malformed forms and path/key disagreement without repair or normalization—and determines structural overlap (identical or ancestor/descendant) via `LocationPath.contains(...)`; overlap marks a conflicting address domain only, never filesystem continuity. LocationContext creation, acceptance, retirement, and replacement use this policy; Source, binding, filesystem, and indexing workflows do not.
- `LocationContextActivationService.createActive(...)` inserts a caller-supplied ACTIVE REVIEW_REQUIRED context with null evidence in one short transaction. It reserves the SQLite writer before reading all ACTIVE contexts by ascending ID, validates every persisted anchor fail-closed, rejects exact and ancestor/descendant overlaps with the conflicting context ID, then inserts. RETIRED contexts do not block creation. File-backed SQLite integration tests cover structural cases, corrupt stored anchors, invalid requests, and concurrent overlapping attempts with one winner.
- `LocationContextAcceptanceService.acceptReviewRequired(id, expectedRevision, acceptedAtMs, acceptedProbeResult)` accepts a successful macOS/APFS observation captured before the transaction. Under SQLite writer reservation it rechecks the unbound ACTIVE REVIEW_REQUIRED row, expected revision, validated anchor, evidence classification, and caller timestamp. A guarded update changes only continuity status/evidence, revision N to N+1, and update time. The strict 128 KiB version-1 envelope binds the APFS evidence to the row ID and post-acceptance revision. Current ACTIVE + ACCEPTED authority requires envelope ID/revision/anchor equality. RETIRED rows may preserve an earlier envelope revision after retirement increments the row; legacy raw ACCEPTED JSON is not rewritten and cannot pass current-authority validation. Already ACCEPTED is a conflict; reacceptance is not implemented. File-backed tests cover failures and five acceptance/retirement/replacement writer-order races.
- `LocationContextRetirementService.retireActive(id, expectedRevision, retiredAtMs)` reserves the same SQLite writer, reads the target and checks for bound Sources, then retires only an ACTIVE row at the expected revision with a valid anchor and non-regressing caller timestamp. It increments revision once, changes only lifecycle and update time, and returns the persisted row. Missing, stale, already-retired, bound, corrupt-anchor, timestamp-regression, and overflow cases fail without mutation. File-backed tests prove two retirements serialize and that overlapping creation can proceed after retirement commits.
- `LocationContextReplacementService.replaceActive(oldId, expectedRevision, replacedAtMs, newContext)` reserves the writer, enforces the same old-row retirement guards, validates all other ACTIVE anchors, and retires the old row before inserting a different-UUID ACTIVE row at the same decoded anchor in one transaction. The new row must be `REVIEW_REQUIRED` with null evidence and creation time equal to `replacedAtMs`; its valid caller revision and update time are preserved. Source bindings are never changed. A failed insert rolls back retirement. File-backed tests cover invalid inputs, corruption, Source references, overlap, historical-ID collision rollback, and races with replacement, retirement, and overlapping creation.
- The location package defines separate typed v1 macOS local-APFS LocationContext and Source-root baselines, plus a strict acceptance envelope binding context evidence to the context ID and accepted revision. Strict deterministic 128 KiB-bounded codecs validate exact schemas, profiles, canonical UUIDs, unsigned-decimal inode/device identities, full-precision birth time, and structured path/key agreement. Pure comparison returns bounded outcome/reason enums, ignores acceptance timestamps and diagnostics, verifies Source/context revisions and structural containment, and mutates nothing.
- The dormant macOS host boundary enumerates every Unix path component to preserve observed case/Unicode spelling, rejects symlink and non-directory boundaries with no-follow checks, directly runs bounded `diskutil info -plist <path>` twice without a shell, and structurally accepts only local APFS type plus a valid, stable Volume UUID. It captures required NIO inode/type/link evidence and Source creation time, checks identity and spelling across the provider observations, and emits typed evidence only for an internally stable accepted result. It has no persistence, binding, transaction, API, or indexing caller. Windows, network/removable filesystems, reboot continuity, APFS clone/restore collisions, and broader race closure are not claimed.

- `POST /api/indexing-runs` accepts a required full UUID and 1–1,000 distinct positive Source IDs. New requests return 202 and Location; exact same-key/Source-set replays return 200 without resubmission, regardless of terminal state. Source order is insignificant, key text is normalized to lowercase, key misuse returns 409, invalid input returns 400, and unknown Sources return 404. A new attempt requires a new key.
- Public acceptance commits ScanRun/request key, Source rows, v2 Job, and DISCOVERY stage together, then submits through the existing background executor. Exact SQLite constraint translation distinguishes a losing request-key race from global v2 admission conflict and other integrity failures. Admission conflict rolls back all new records; scheduling rejection returns 503 and leaves an inspectable failed attempt, which exact replay returns unchanged.
- `GET /api/indexing-runs/{scanRunId}` returns a consistent durable snapshot with stages, persisted progress/timestamps, safe errors, and typed assignment/hash results. Raw result JSON and internal result versions are not exposed. Malformed durable summaries fail safely with 500 and IDs logged. `completedWithIssues` is derived only from completed hashing skips/failures; no new durable status exists.
- `GET /api/indexing-runs/source-status` returns the active v2 summary and latest v2 execution per registered Source, including null latest values. Two SQL queries in one read transaction avoid N+1 behavior. Latest uses ScanRun creation time and ID; Sources sort by ID. Both polling GETs are read-only and no-store. Public v1 endpoints remain available; React now uses the v2 contract, while SSE/cancellation/retry/resume remain deferred.

- Catalog ownership uses Java NIO `FileChannel.tryLock()` on a `.lock` sidecar derived from `spring.datasource.url`. Ownership precedes datasource/Flyway initialization, lasts through shutdown, and prevents a second backend from using the same local catalog. The sidecar is retained; the OS lock is authoritative.
- After schema initialization and before executor availability, startup recovery atomically fails each interrupted active v2 SCAN Job and nonterminal ScanRun. Only the current running stage fails; pending stages remain unclaimed and completed stages/results survive. Malformed state aborts startup with durable IDs in logs.
- Recovery fails actively discovering Source rows but preserves discovered evidence, committed Source reconciliation boundaries, observations, content associations, and hash artifacts. It never runs a missing sweep, resumes a stage, retries, or reopens a terminal Job. Version-1 executions remain untouched.
- The internal `Version2BackgroundIndexingService.start(scanRunId)` creates/commits v2 execution before submission and returns durable identity. Ambient transactions are rejected. A dedicated named worker has core/max size one, one queue slot, and abort rejection; it invokes the existing coordinator without a pipeline-wide transaction.
- Scheduling rejection terminally fails the accepted execution and releases admission. Escaping worker failures inspect and finalize still-active durable state; normal terminal failures remain intact. Finalization persistence failure is logged and requires startup recovery.
- Shutdown stops submission and waits up to 30 seconds, then interrupts unfinished work. Cooperative checks distinguish interruption from ordinary candidate issues. If a worker outlives the budget, ownership remains held until process exit to prevent another backend recovering live work.

Changed traversal identity alone remains safe. Hashing leaves FileEntry, ContentRecord, ScanRun, ScanRunSource, Job, and JobStage state unchanged and creates no new execution rows.

- Media-metadata schema version 1 stores typed `AVAILABLE` image/video payloads or `UNSUPPORTED` in `analysis_record.result_json`; strict codecs reject incompatible shapes and invalid domain states. Readers/streams are disposed/closed, extraction is outside transactions, and stale occurrences fall through to later current occurrences.

Individual extraction failures complete the Job with issue counts; unexpected infrastructure failures fail the stage and Job.

Startup fails abandoned active metadata Jobs and changes only exact `builtin.imageio` `PENDING`/`RUNNING` analysis rows to retryable `FAILED`; completed artifacts survive. Scheduling rejection fails both the accepted Job and stage, and shutdown follows the existing bounded ownership-safe worker convention.

- `FfprobeMediaMetadataInterpreter` strictly projects canned ffprobe JSON into a small typed model, rejects malformed consumed fields through an explicit failed-interpretation result, and produces either the existing typed VIDEO payload or `UNSUPPORTED`. It normalizes container/codec identifiers, converts `format.duration` to rounded microseconds, applies default-first deterministic primary-stream selection, excludes artwork/thumbnails/still streams, rejects image-oriented and external presentations, and uses focused ISO BMFF image-brand evidence without a positive video-container allowlist. It has no subprocess, filesystem, database, or Job behavior.
- `FfprobeProcessRunner` lazily qualifies an absolute path explicitly configured through `media-compare.ffprobe.executable` or, when absent, the default `ffprobe` PATH command, then invokes a fixed no-shell argument vector. It redirects the validated regular file to stdin and probes only `fd:` with protocol whitelist `fd`, disabled MOV external references/absolute paths, selected JSON fields, a 30-second timeout, a 4 MiB stdout limit, and a 256 KiB stderr limit. Output streams drain concurrently; overflow, read failure, and interruption promptly wake the owner for bounded graceful/forced cleanup, while timeout triggers that same cleanup. A probe's nonzero exit, invalid UTF-8, timeout, or output-limit breach is a per-content probe failure; process-facility, stream-reader, and cleanup failures remain infrastructure failures. The runner performs no catalog validation, persistence, or Job work.

## Known Limitations / Not Yet Implemented

- No Source update, deletion, or relocation/remount recognition workflow exists.
- No general ScanRun list, cancellation/retry/resume, WorkingSet request, or custom indexing options API exists.
- Normal v1/v2 creation excludes competing ScanRun ownership under SQLite write reservation. Database admission indexes still apply only to version-2 SCAN Jobs.
- No materialized equality-group identity, ContentRecord reconciliation/merge, durable video extraction/publication, perceptual fingerprints, embeddings, face analysis, or AI integration exists. The pure video interpreter, bounded ffprobe runner, and catalog-global image-only media-metadata Job/manual API are implemented; durable video integration, automatic scheduling, and frontend metadata display remain deferred.
- No general scheduler, pause/resume, or live progress delivery exists; the dedicated internal v2 worker and fail-on-startup recovery are implemented.
- No SSE endpoint or event design exists.
- No automatic indexing retry or resume exists. Refresh/navigation reconstructs durable active/latest v2 state, while interrupted backend work retains the existing fail-on-restart behavior.
- No matching candidates, similarity relationships, materialized groups, manual overrides, or filesystem-action history exists.
- No broader Library/Review UI, review states/flags, persistent categories/tags, AI suggestions, similarity-group UI, or actual filesystem actions exist.
- Advanced sorting is deferred; the frontend preserves deterministic server digest ordering rather than sorting only loaded pages.
- Public indexing retry/resume, metadata scheduling beyond the one-active constraint, merge behavior, cache locations, and real-Windows ffprobe `fd:` acceptance remain open as documented.
- The approved overlapping-Source and multiple-catalog runtime architecture is not yet implemented: ACTIVE LocationContext creation, explicit acceptance, retirement, and same-anchor replacement are available, but Source binding and operational continuity checks are not wired to them. The current schema still gives each FileEntry one `source_id`, owns presence on FileEntry, and uses one configured SQLite database per backend context. There is no bound-context replacement/rebinding workflow, SourceMembership table, shared FileEntry resolution, catalog registry/switching, archive export, passive restore UI, or standalone hashing Job.
- The frontend still has no automated test framework. Frontend validation remains lint and a production TypeScript/Vite build; durable component tests remain a future testing-infrastructure decision.
